2. **Merge-tag slugs** are computed, not hand-typed, from each field's actual provisioned GHL display name via the identical `expectedFieldKey()` function every INV-67 batch-provisioning script already uses and that GHL's own API confirmed at readback time. Per this task's literal instruction, the merge tag is rendered **with internal spaces** -- `{{ opportunity.<slug> }}` -- for this manifest; this is a display convention for Spock's placement pass, not a claim that GHL requires the spaces (the batch scripts render the same tag without spaces, `{{opportunity.<slug>}}`; both forms resolve to the identical `fieldKey`).

3. **"Placement guidance" is PDF-text-derived, not a proven GHL coordinate.** No authenticated GHL template-editor session was available to this build; nothing below claims an x/y pixel position inside GHL's editor. Guidance describes which printed word, checkbox, or blank each field must sit on/beside, using the PDF's own line-level reading order. Where two or more blanks share one printed line in a way that cannot be disambiguated from text alone, the row is classified **"Visual judgment"** rather than "Ready".

4. **Two genuinely ambiguous printed-checkbox orderings were caught and corrected** rather than assumed symmetric: paragraph 6A(8)(ii)'s "at the expense of q Buyer q Seller" prints Buyer's checkbox first, while paragraph 6C(1)'s "at q Seller's q Buyer's expense" prints Seller's checkbox first -- each row below is written against its own actual printed word order, not a copy-pasted assumption from the other.

5. **This regeneration's own new methodology note:** the two new SPLIT destinations (paragraph 5(1) and 9A) inherit their PAGE attribution from the original manifest's own already-corrected page map (see "Independent PDF re-verification" above) rather than from a fresh, unvalidated re-derivation -- their PRINTED TEXT was independently re-confirmed fresh this session.
